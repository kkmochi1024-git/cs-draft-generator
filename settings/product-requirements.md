# プロダクト要求定義書 (PRD)

## プロダクト概要

### 名称
**CS Draft Generator** - カスタマーサポート回答ドラフト生成システム

### プロダクトコンセプト
- **PII安全なAI活用**: 個人情報を自動マスキングした上でLLMに渡し、情報漏洩リスクを排除する
- **RAGベースの回答生成**: 過去の問い合わせメール・製品マニュアルを参照し、文脈に即した回答ドラフトを生成する
- **LLM切替可能**: マスキング精度の検証状況に応じてローカルLLM/クラウドLLMを切り替えられる

### プロダクトビジョン
カスタマーサポート担当者がメール対応にかける時間を大幅に削減する。過去の問い合わせ対応と製品マニュアルをAIが参照し、高品質な回答ドラフトを自動生成する。PIIの自動マスキングにより、個人情報を含むメールでも安全にAIを活用できる環境を実現する。

### 目的
- サポート担当者の回答作成時間を50%以上削減する
- 回答品質を担当者の経験に依存しない水準に標準化する
- PIIを外部に流出させずにLLMを活用可能にする

- **期待する解決策**: 質問を入力するだけで過去事例を踏まえた回答ドラフトが得られる
- **1日の典型的なワークフロー**: Zendesk/Outlookで新着チケット確認 → 過去メール・マニュアル検索 → 回答作成 → レビュー → 送信

### セカンダリーペルソナ: 田中太郎（45歳、サポートチームリーダー）
- **経験**: マネジメント5年、技術的知識あり
- **現在の課題**: チームの回答品質にばらつきがある。新人の立ち上がりに時間がかかる
- **期待する解決策**: ナレッジが自動的に蓄積・活用され、チーム全体の品質が底上げされる

## 成功指標（KPI）

### プライマリーKPI
- 回答ドラフト生成の利用率: サポート担当者の80%が日常的に使用（運用開始3ヶ月後）
  - 測定方法: 月間アクティブユーザー数 / サポートチーム人数
- 回答作成時間の短縮: 1件あたり平均10分 → 5分以下（運用開始1ヶ月後に測定）
  - 測定方法: Zendeskチケットの first response time の導入前後比較

### セカンダリーKPI
- PIIマスキング検出率: 95%以上（クラウドLLM切替の判断基準）
  - 測定方法: アノテーション済みテストデータセット（100件）での検出数 / 実際のPII数
  - 検出率に加えて誤検出率も算出し、あわせて評価する
  - 検出漏れパターンを分析し、マスキングルールを継続改善する
- 回答ドラフトの採用率: 生成されたドラフトの60%以上がそのまま or 軽微な修正で使用される（運用開始3ヶ月後）
  - 測定方法: 担当者へのアンケート（月次）

## 機能要件

### コア機能（MVP / P0）

#### PIIマスキング

**ユーザーストーリー**:
サポート担当者として、顧客情報を含むメール文を安全にAIに渡すために、個人情報を自動的にマスキングする機能が欲しい

**受け入れ条件**:
- [ ] メールアドレス・電話番号・郵便番号を正規表現で検出・マスキングできる
- [ ] 人名・住所をGiNZA NERで検出・マスキングできる
- [ ] マスキング結果をプレビュー表示し、ユーザーが確認できる
- [ ] マスキングマッピングを保持し、回答生成後にアンマスク（復元）できる
- [ ] マスキングのみの単独実行ができる（RAG・LLMなしで動作）

**優先度**: P0（必須）

#### RAGデータ登録

**ユーザーストーリー**:
サポート担当者として、過去のメール対応をAIの参照データとして蓄積するために、テキストをマスキングしてRAGに登録する機能が欲しい

**受け入れ条件**:
- [ ] テキスト入力をマスキング → チャンク分割 → Embedding → ChromaDBに登録できる
- [ ] 登録時にメタデータ（日時、ソース種別）が付与される
- [ ] 登録済みデータの件数を確認できる

**優先度**: P0（必須）

#### RAG回答生成

**ユーザーストーリー**:
サポート担当者として、新規の問い合わせに対して過去事例を踏まえた回答ドラフトを素早く得るために、質問を入力するとAIが回答を生成する機能が欲しい

**受け入れ条件**:
- [ ] 質問テキストで類似の過去メールを検索（上位5件）できる
- [ ] 検索結果を参照してLLMが回答ドラフトを生成できる
- [ ] 回答内のマスクトークンがアンマスクされて表示される
- [ ] 参照元ドキュメントが表示される

**優先度**: P0（必須）

### 重要機能（P1）

#### .emlファイル一括登録

**ユーザーストーリー**:
サポート担当者として、過去のメールを効率的にRAGに取り込むために、.emlファイルを指定して一括登録する機能が欲しい

**受け入れ条件**:
- [ ] .emlファイルからメール本文・件名・日時を抽出できる
- [ ] ディレクトリ指定で複数ファイルを一括処理できる
- [ ] スレッド構造から問い合わせ/回答のペアを検出できる

**優先度**: P1（重要）

#### 製品マニュアル取り込み（PDF）

**ユーザーストーリー**:
サポート担当者として、製品マニュアルの内容もAIの参照データに含めることで、マニュアルに記載のある質問にも正確に回答できるようにしたい

**受け入れ条件**:
- [ ] PDFファイルからテキストを抽出できる
- [ ] 抽出したテキストをチャンク分割 → Embedding → ChromaDBに登録できる
- [ ] 複数PDFファイルの一括処理ができる
- [ ] 登録時にメタデータ（ファイル名、ページ番号）が付与される
- [ ] 回答生成時にマニュアルの参照箇所（ファイル名・ページ）が表示される

**優先度**: P1（重要）

#### WebアプリUI（チャット形式）

**ユーザーストーリー**:
サポート担当者として、ブラウザから直感的に使えるチャット形式のUIで回答生成を行いたい

**受け入れ条件**:
- [ ] ChatGPTライクなチャットUIで質問・回答の対話ができる
- [ ] マスキング結果のプレビュー・手動修正ができる
- [ ] LLMバックエンド（ローカル/クラウド）をUIから切り替えられる
- [ ] .emlファイル・PDFファイルをアップロードして登録できる

**優先度**: P1（重要）

#### Zendesk API連携

> ヘルプデスクSaaSの代表例として Zendesk を対象に設計する。同種のREST APIを持つ他サービスにも同じ構造で対応できることを前提とする。

**ユーザーストーリー**:
サポートチームリーダーとして、ヘルプデスクSaaSのチケットを自動的にRAGに取り込むことで、手動のデータ登録作業をなくしたい

**受け入れ条件**:
- [ ] Zendesk APIでチケット・コメントを取得できる
- [ ] 差分取得（前回以降の新規・更新チケットのみ）ができる
- [ ] 定期バッチ実行（cron）に対応している

**優先度**: P1（重要）

### 将来機能（P2）

- クラウドLLM自動切替: マスキング精度が基準を達成した場合にクラウドLLMを自動選択
- 回答テンプレート管理: よく使う回答パターンのテンプレート化
- 多言語対応: 英語での問い合わせ対応

## 非機能要件

### パフォーマンス
- Embedding生成: 1チャンクあたり1秒以内
- ChromaDB類似検索: 1秒以内
- 回答生成（ローカルLLM）: 1〜2分（Gemma 4 12B (Q4) / CPU / 16GB RAM）
- 回答生成（クラウドLLM）: 10秒以内

### ユーザビリティ
- CLIモード: サポート担当者が5分以内に基本操作（登録・質問）を実行できる
- WebアプリUI: 追加の学習なしで操作できるChatGPTライクなインターフェース

### 信頼性
- ChromaDBのデータはDockerボリュームで永続化し、コンテナ再起動でデータが消失しない
- マスキングマッピングはセッション単位で生成・破棄（永続化しない）

### セキュリティ
- PIIを含む生データはVector DBに格納しない（マスキング済みのみ保存）
- クラウドLLM利用時はマスキング済みテキストのみ送信
- APIキー等の秘匿情報は `.env` で管理し、Gitにコミットしない
- マスキングマッピングテーブルはログ・キャッシュに書き出さない

## 技術的制約

- ハードウェア: 16GB RAM / CPU環境（GPU なし）で動作すること
- OS: macOS / Windows / Linux のクロスプラットフォーム対応
- コンテナ: アプリはDockerコンテナ内で動作、OllamaはホストOS上で動作
- LLM: ローカルは Ollama + Gemma 4 12B (Q4)、クラウドは Claude API

## スコープ外

以下はこのプロダクトの対象範囲外とする：

- メールの自動送信（回答ドラフトの生成まで。送信は人間が行う）
- リアルタイムチャットボット（非同期のメール対応が対象）
- Outlook直接接続（Microsoft Graph API）— 将来検討
- ユーザー認証・マルチテナント — 社内ツールのため不要
