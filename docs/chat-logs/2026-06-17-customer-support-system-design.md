# カスタマーサポート回答生成システムの設計

- **日時**: 2026-06-17
- **参加者**: ユーザー, Claude

## 背景・目的

SaaS製品のカスタマーサポート（メール対応）をAIで効率化したい。メールにPIIが含まれるためクラウドLLMにそのまま渡せない課題を、PIIマスキング + ローカルLLMで解決するアプリを設計する。

## 議論の要点

### アーキテクチャ方針

- **結論**: RAG + PIIマスキング + LLM（ローカル/クラウド切替可）構成を採用
- マスキング精度が検証されるまではローカルLLMをデフォルトとし、検証後にクラウドLLM（Claude API）に切り替える

### PIIマスキングの自動化

- **ユーザーの懸念**: 手動マスキングは非現実的
- **結論**: 正規表現（メアド・電話番号等）+ GiNZA NER（人名・住所）の2層構成で自動化。精度は完璧ではないが、クラウド送信リスク低減の目的には実用十分

### LLMモデル選定

- **ユーザーの提案**: Gemma 4 12B、スペックは16GB RAM / CPU
- **結論**: Gemma 4 12B (Q4量子化) を採用。動くが回答生成に1〜2分かかる。品質・速度重視ならマスキング後のクラウドAPI利用を推奨（B案）
- **却下案**: ローカルLLMのみで完結する案 → 回答品質・速度がクラウドに大きく劣るため、マスキング精度検証後はクラウドに移行する方針に

### RAG vs Agentic Search

- **ユーザーの質問**: Agentic Searchの方が良いのでは？（Zenn記事参照）
- **結論**: RAGが適切。理由: メール本文は非構造的な自然言語であり、grep等では「意味的に似た問い合わせ」を見つけられない。Agentic Searchは構造化された情報の探索に向いている

### コンテナ化

- **結論**: アプリ側はDockerコンテナ化する。Ollama（ローカルLLM）はホストOS上で動作させる
- **却下案**: Ollama含めて全コンテナ化 → 16GB RAMでコンテナオーバーヘッド分のメモリが不足するリスク、GPU パススルーの複雑さ、Ollama自体が既にHTTPサーバーとして設計済みのため不要

### クロスプラットフォーム対応

- **結論**: macOS / Windows / Linux で動作する設計。Docker Desktop + ホストOllamaの構成はいずれのOSでも共通。ファイルパスは `pathlib.Path` を一貫使用

### モジュール分離（サービスインターフェース）

- **ユーザーの要望**: マスキングだけを単独利用したい
- **結論**: MaskingService / IndexService / QueryService の3サービスに分離。デプロイは1コンテナ（マイクロサービス化はオーバーエンジニアリング）だが、コード上は疎結合。将来HTTP APIに切り出す際も最小変更で移行可能
- **却下案**: プロトタイプ段階でのマイクロサービス化 → 16GB環境で複数コンテナは厳しい、個人〜少人数の社内ツールでスケールメリットがない

## 決定事項

- 設計書は `settings/` フォルダで管理（INDEX.md でインデックス管理）
- D-000: マスター設計書（全体アーキテクチャ）
- D-001: プロトタイプ（テキスト入力 → マスキング → RAG → CUI回答生成）
- D-002: 第1弾アップデート（.emlファイル読み取り）
- D-003: 第2弾アップデート（Streamlit WebUI）
- D-004: 第3弾アップデート（Zendesk API連携）
- プロジェクトローカルスキル: `/save-chat`（会話履歴保存）、`/log-app-change`（変更履歴記録）
