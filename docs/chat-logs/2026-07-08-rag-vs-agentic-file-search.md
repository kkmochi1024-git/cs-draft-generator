# RAG vs エージェント的ファイル探索の比較検討

- **日時**: 2026-07-08
- **参加者**: ユーザー, Claude

## 背景・目的

本システム（CS Draft Generator）は RAG（ChromaDB ベクトル検索）で問い合わせ回答ドラフトを生成しているが、Claude Code や Codex のように「プロジェクト上の Markdown 等のテキストファイルを直接読み込ませて生成する方式」の方が良いのではないか、という疑問が出発点。それぞれのメリット・デメリットと、**生成元データが増えたときにどちらがパフォーマンス・生成精度で優れるか**を検討した。

## 議論の要点

### 論点1: 「Claude Code 方式」の正体

- **ユーザーの質問**: Markdown ファイルを読み込ませる方式の方が良いのでは？
- **AIの回答**: Claude Code は「全ファイル読み込み」ではなく**エージェント的探索**（grep / ls / read のツールループを LLM が操縦）。比較対象は正確には3方式ある：①全文脈投入（全ファイルをプロンプトに詰める）②エージェント的探索 ③RAG（現行）
- **結論**: 3方式を比較軸に沿って評価する

### 論点2: 比較評価（観点は Claude が追加拡張）

比較観点: パフォーマンス（ユーザー指定）・生成精度（同）に加え、**必要モデル能力・PII保護との親和性・データ鮮度と運用コスト・引用可能性・データ規模への耐性**を追加。

- **RAG の強み**: レイテンシ（埋め込み1回＋LLM1回）、言い換え耐性（意味検索は問い合わせ文とマニュアルの語彙差を吸収）、弱いモデルでも成立、登録時1回のマスキングで済む PII 親和性、出典明示（📄 p.23 等は実装済み）
- **RAG の弱み**: チャンク分割で文脈が切れる（多段推論・全体把握に弱い）、再インデックス運用、埋め込み・チャンク戦略の保守コスト
- **エージェント探索の強み**: 疑問を持ちながら掘り進む多段推論、索引不要でデータ鮮度が常に最新、Git 差分管理と相性が良い
- **エージェント探索の弱み**: ツールループで LLM を5〜20回呼ぶためレイテンシが数十秒〜数分、grep はキーワード一致前提で言い換えに弱い、**的確なツール使用判断ができる最上位クラスのモデルが必要（ローカル12Bクラスでは探索が迷走しやすい＝本システムでの決定的障害）**、生ファイルを読むたびマスキングが必要
- **全文脈投入**: 数十ファイル（数万トークン）までは最高精度だが、それを超えるとコンテキスト窓超過または「中間情報の見落とし（lost in the middle）」で劣化。コスト・レイテンシもトークン量に比例悪化

### 論点3: データが増えたときの優劣（質問の核心）

- **AIの回答**: **RAG が明確に優位**。ベクトル検索は近似最近傍探索のため検索コストがほぼ規模非依存（ChromaDB は百万チャンク級まで実用的）。エージェント探索は非構造なメールの山では「どこから読むか」の当たりを付ける手段が grep しかなく探索が破綻する。Claude Code が探索方式で成功しているのは、コードベースが**意味のあるファイル名・構造・シンボルを持つ構造化データ**で、かつ最上位モデルが操縦しているから。CS メール履歴は前提が根本的に異なる
- **明示した推測**: 「ローカル12Bで探索ループが迷走しやすい」は一般傾向からの推測で gemma での実測はなし（ただしリスクの方向は確度が高い）。D-006（クラウドLLM切替）後は技術的に探索方式も可能になるが、探索のたびに大量のマスク済みテキストを外部送信することになりコストと PII 露出面が増える

## 決定事項

- **RAG 継続が正解**。根拠: ①ローカル12BクラスのLLM（エージェント探索に必要なモデル能力を満たさない）②CS業務のレイテンシ要件 ③登録時マスキングというPII保護設計との整合 ④増え続ける非構造メール履歴という データ特性
- **却下した選択肢**: エージェント的探索への全面移行（モデル能力・レイテンシ・PII面で不利）、全文脈投入（規模で破綻）
